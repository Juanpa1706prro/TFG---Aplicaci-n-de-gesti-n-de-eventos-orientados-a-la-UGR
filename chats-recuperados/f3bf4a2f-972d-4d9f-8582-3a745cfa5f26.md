## Idea central: separar “cuenta” de “perfiles”

Tu profesor apunta al patrón correcto:

1. **`users` (o `accounts`)**  
   Solo identidad y autenticación: email, hash de contraseña, tokens, fechas. **No** mezclar aquí “soy secretario” o “soy doctorando” como un único enum global si puede haber varias facetas.

2. **Estudiante solo → tabla `students` (o `student_profiles`)**  
   Datos propios de alumno: expediente, titulación, curso, centro, lo que necesites para eventos/asistencia. Relación típica: `user_id` único (1 usuario ↔ 0 o 1 fila estudiante, o 1:N si en el futuro admites varias matrículas).

3. **Personal UGR → tabla de personal (empleo / afiliación)**  
   Por ejemplo `staff_affiliations` con campos como tipo de colectivo (`PROFESSOR`, `SECRETARIA`, `BIBLIOTECA`, `SEGURIDAD`, `RECTORADO`, `OTROS`…), departamento/servicio, fecha alta/baja. Un mismo `user_id` puede tener **varias filas** si tiene varios contratos o roles administrativos distintos (si no quieres eso al principio, una fila con un `primary_role` y JSON opcional de roles secundarios también vale para el TFG).

4. **Quien es estudiante y personal**  
   Ese usuario tendría **las dos cosas**: fila en `students` y fila(s) en `staff_affiliations`. No hace falta duplicar cuentas.

5. **“Con qué perfil entro ahora”**  
   No sustituye al modelo de datos: es **contexto de sesión**:
   - Tras el login, el backend devuelve `availableProfiles: [{ type: 'STUDENT', id: 1 }, { type: 'STAFF', id: 7 }]`.
   - El usuario elige (pantalla obligatoria si `length > 1`).
   - Emites un access token (o sesión) que incluya algo como `activeProfileType` + `activeProfileId` (o códigos estables).
   - Las reglas de eventos (crear, moderar, inscribirse) se evalúan contra **ese contexto activo**, no solo contra `users.role`.

Así evitas explosión de enums tipo `STUDENT_WHO_IS_ALSO_PROFESSOR` y mantienes una sola cuenta.

## Permisos y eventos

Te conviene **no** mapear “tipo de personal UGR” 1:1 con “puede crear eventos”. Mejor:

- Un **delegado** o “estudiante con permisos” sería: perfil estudiante + registro en algo tipo `student_privileges` o rol de aplicación ligado al perfil, no un tercer tipo de usuario duplicado en la misma tabla.
